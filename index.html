1 · The pipeline

What happens on every pull request

Click a stage to see what it runs, why it is there and what makes it fail. A failure at any stage turns the required check red and GitHub blocks the merge.

2 · Where the scan runs

Two containers on one Docker network

The app and ZAP share a network, so ZAP reaches Flask by its container name. Reports are written through a bind mount and uploaded as an artifact.

Target: http://devsecops-web:5000/welcome. The upload step runs even after earlier failures, and fails if no report file exists.

4 · Experiments

Three experiments, three lessons

Change one thing, observe the result, and write down what it does and does not prove.

Does Bandit block a hardcoded password?

1 · Baseline

d380ee6 adds Bandit to CI. The scan passes.

2 · Introduce

29adbcc adds a dummy hardcoded password. Bandit reports B105; the required check blocks merging.

3 · Cosmetic fix

3b4148a renames password to value. The scan passes, but the hardcoded string is still there.

4 · Real fix

7a2e4e9 removes the unused dummy value. No issues; both tests pass.

Lesson: a passing SAST check does not prove the code is secure. A reviewer still has to check that the underlying problem was fixed. Only synthetic data was used. Notes.

ZAP finds a missing header, and the fix is verified three ways

Finding

ZAP rule 10021: X-Content-Type-Options header missing on / and /welcome.

Fix

One after_request hook sets nosniff on every response.

Pin it

A new pytest test asserts the header so it cannot regress silently.

Verify

All tests pass, curl shows the header, and the follow-up ZAP report no longer lists 10021.

@app.after_request
def add_security_headers(response):
    response.headers["X-Content-Type-Options"] = "nosniff"
    return response

def test_welcome_has_nosniff_header():
    client = app.test_client()
    response = client.get("/welcome")
    assert response.headers.get("X-Content-Type-Options") == "nosniff"
Lesson: fixing one finding does not make the app secure; other alerts remain (see Findings). Rule 10021 stays configured as FAIL in .zap/baseline.conf.

Can a ZAP finding block a merge?

The existing CSP finding (rule 10038) was temporarily set to FAIL in pull request #5.

ZAP

Reported 10038 as FAIL and exited with code 1.

Required check

The check failed and GitHub blocked the merge.

Reports

HTML and JSON were still uploaded despite the failed scan.

Revert

Removing the temporary policy made CI pass again.

What it provesA ZAP finding configured as FAIL can block a merge.
What it does not proveIt did not fix the missing CSP header, and it did not test a regression of rule 10021.

Config: .zap/baseline.conf holds one tab-separated line, 10021 FAIL (X-Content-Type-Options Header Missing). The -I option only affects WARN findings. Notes.

6 · Run it yourself

Reproduce the checks locally

Windows PowerShell, from the repository root. Needs Git, Python 3.13 and Docker Desktop with Linux containers.

Tests and SAST 
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m bandit app.py
Build and start the app 
docker build -t devsecops-lab:local .
docker network create devsecops-net
docker run --rm --name devsecops-web --network devsecops-net -p 127.0.0.1:5000:5000 devsecops-lab:local

# second terminal
curl.exe -i http://127.0.0.1:5000/welcome

Expected: HTTP 200, the welcome message and X-Content-Type-Options: nosniff.

ZAP Baseline 
New-Item -ItemType Directory -Force reports/raw
Copy-Item .zap/baseline.conf reports/raw/baseline.conf
$zapReportPath = (Resolve-Path reports/raw).Path

docker run --rm --network devsecops-net --mount "type=bind,source=$zapReportPath,target=/zap/wrk" ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t http://devsecops-web:5000/welcome -c baseline.conf -I -r zap-local.html -J zap-local.json

$LASTEXITCODE

Reports land in reports/raw/. With -I, WARN findings do not fail the scan; FAIL findings still do. A clean exit does not mean the app has no findings.

Limitations

What this lab does not claim

  • The app uses Flask's development server. It is a lab, not a production deployment.
  • ZAP Baseline crawls and scans passively. It is not a full active assessment.
  • CSP and other reported warnings are still unresolved.
  • Passing tests and scans do not prove the application is secure.
  • Docker images use mutable tags, so later runs may use different versions.
  • Security testing is limited to this lab. Only synthetic data and dummy credentials are used.
A learning project on how security checks fit into CI/CD. See the repository for the code, workflow and notes.
